# 主題日曆與 AI 發文第一版開發規格

第一版驗證一條完整流程。承辦人在日曆建立主題並匯入素材，AI 自行推斷發文目的、選擇切入點，必要時查找公開資料，產出一篇貼文。AI 從主題期間內的既有發文時段挑選一個，由系統核對時段並排入現有佇列。單位啟用自動發文後，通過 AI 審核的有效版本到點即可發布。承辦人可以預覽、編輯、鎖定或暫停。

## 產品範圍與品質驗收

| 訪談題次 | 第一版決策 |
| --- | --- |
| 價值 1 | 省下人工時間是預期效益。驗收聚焦成品品質，取消人工時間減半的門檻。 |
| 價值 2 | 每個案例提供一個主題與一批素材，驗證 AI 能否自主找角度並交付一篇可發布的貼文。 |
| 價值 3、4、6 | 依發文目的衡量讀者得到什麼，並按目的分配篇幅。知識分享要講清楚實質觀念。活動通知要交代活動在做什麼、時間、地點與參加方式等必要資訊。有趣或能幫讀者理解的時事都是品質加分，適合時才使用。 |
| 價值 5 | 可以用迷因或網路熱梗。沒看過原梗的讀者也要能看懂情境與正文。讓不同年齡的讀者都能會心一笑，另外加分。 |
| 價值 7 | AI 從主題與素材推斷這篇的發文目的，承辦人只須提供主題與素材。 |
| 價值 8 | 讓目標讀者匿名試讀現行流程稿與 AI 稿，回答「看完知道了什麼」等與目的相符的問題。承辦人逐篇核對關鍵事實、來源、單位語氣與可發布性。 |
| 價值 9、10 | 學校、協會和公司都納入試讀，合併判定整體品質。各篇仍須通過可發布性核對。 |

同一主題在第一版只排一篇貼文，可沿用現有各平台版本。系列貼文、預告與回顧、固定資料夾自動匯入，以及發布後的成效管理，列入後續版本。

## 功能與技術規格

### 日曆、素材與佇列

- **主題與時段（技術 7）。** 主題包含名稱及單日或日期區間，日期以台北時區計算。AI 從現有週期時段選一個，後端驗證時段在主題區間內、仍在未來且可用。區間內沒有可用時段時，日曆顯示原因。時段預覽顯示預定稿、備稿或審核進度、素材來源及換稿原因。不同主題爭用同一時段時，建議由 SQLite 保證一個時段只能綁一個主題，衝突的主題改選其他可用時段。
- **素材匯入。** 從主題頁拖放文字檔與照片，也能貼文字或匯入網址。沿用現有文字、網址及圖片入口，新增素材與主題的關聯，並保存產稿實際使用的素材版本。首批檔案格式建議為 TXT、JPG、PNG。文字以原文段落定位，支援具有頁碼的格式時再顯示檔案頁碼。[現有素材入口](../selfhost/server.mjs#L117)
- **接上佇列。** 將未來的時段綁定與到點後的發佈紀錄分開保存。到點優先選取仍有效、已通過審核的綁定稿，再沿用既有的一般稿、備稿與略過規則。綁定主題稿不得被其他週期時段提前取走。改期時重新核對受影響的未發綁定，保留區間內仍適用的時段。已發送的平台結果保留在原發佈紀錄。[選稿與發佈入口](../selfhost/engine.mjs#L113)

### 查找來源、產稿與審核

- **搜尋範圍與權限（技術 1、10）。** AI 先讀匯入的素材與既有來源，需要時才提出公開網路查詢。後端負責查詢及擷取，驗證網址和轉址，限制請求量，保存網址、擷取時間及採用的原文片段。網頁內容只供產稿與審稿參考。AI 與搜尋工作不持有發佈憑證，平台發送由既有發佈流程執行。
- **事實衝突（技術 2）。** 影響發文目的的資訊若有衝突，例如活動時間或報名方式不同，保留草稿、列出兩份證據、暫停自動發布，等承辦人確認。開場用的時事或熱梗若查不清楚，AI 改用其他切入點。
- **獨立審稿（技術 3、4）。** 使用同一模型做兩次獨立呼叫。第一次產稿，第二次以稿件與當時保存的來源審核目的達成度、關鍵事實、跨年齡可讀性及各平台實際文案。未通過時允許依理由改寫一次再審，關鍵事實衝突仍須承辦人確認。每項關鍵事實在內部預覽連到支持它的原文段落或檔案頁面，公開文案維持自然。核准記錄標示 AI 或人工，並綁定稿件與引用來源版本。[現有核准流程](../selfhost/server.mjs#L175)

### 換稿、發送與重啟復原

- **換稿期限（技術 5、6）。** 自動改寫工作須在發文前 24 小時的截止點前開始。已開始的候選稿可以在截止後完成審核，於發文前通過才自動換版。舊的排定稿在換版成功前保留。到點時若候選稿仍未通過，發仍有效的原稿。手動修改或鎖定後由承辦人決定是否採用新版。日曆同時顯示目前排定版和審核中的候選版，成功換版時記錄原因。
- **關鍵資訊變更。** 一收到關鍵事實或引用素材的修正，立即停用受影響的舊稿與候選稿，即使已過換稿截止或承辦人鎖稿。內容更新後重新審核。到點若沒有可發的主題版，照既有佇列規則補位。
- **交易與發文（技術 8）。** 排程領取時，在 SQLite 交易內綁定時段、稿件版本與審核結果。各平台在呼叫最終發布 API 前，再用短交易檢查排程、稿件、素材與審核版本，並轉為送出中。改期或換稿先提交時，停止舊工作。若工作先轉為送出中，保留該次嘗試及平台結果。外部 API 呼叫在交易外執行，結果不明交由現有核對流程處理。發現變更時若已有部分平台送出，保留已送結果，擋下尚未送出的舊工作，並在介面顯示各平台狀態。[發佈工作與分平台紀錄](../selfhost/engine.mjs#L134)
- **分階段復原（技術 9）。** 每完成來源蒐集、產稿或審核，就持久化結果。重啟後從最後成功提交的階段接續，未提交的階段可重試。用工作識別碼與稿件版本做條件更新，確保舊工作結果無法覆蓋新版，重試也不會重複排稿。產稿工作要包含主題、時段與版本，現有僅按單篇素材識別工作的方式需擴充。[現有產稿工作入口](../selfhost/engine.mjs#L10)

## 實作順序與階段驗收

| 順序 | 實作 | 完成條件 |
| --- | --- | --- |
| 1 | **打通時段綁定與發佈交易。** 用現有人工核准稿建立綁定，接到現有排程與補位。先建立版本檢查和送出前的交易。 | 較早時段取不到綁定稿。到點優先選中，失效能補位。模擬改期與送出並行，改期先提交時擋住舊稿。主機重啟及平台結果不明時不會盲目重送。 |
| 2 | **做主題日曆與素材匯入。** 提供單日與日期區間、時段預覽、素材版本與原文定位。 | 改期可辨識受影響的未發時段。重疊與無可用時段都有明確狀態。草稿預覽能回查素材及引用位置。 |
| 3 | **做自主備稿與重啟復原。** 接上按需搜尋、後端擷取、來源留存、發文目的推斷與每主題一稿。 | 有合適時事、沒有合適時事及選用熱梗的案例都能備稿。搜尋失敗仍可用足夠的主題素材成稿。重啟接續已保存進度，舊結果無法覆蓋新版。 |
| 4 | **做獨立 AI 審核、候選換版及自動發文。** 接上證據對照、失效規則、24 小時截止、人工修改及鎖稿。 | 截止前已開工的候選版可在發文前通過並換版。到點仍未過審則採有效原稿。關鍵事實衝突或變更時擋下舊稿。用模擬平台驗證後，再以測試帳號核對實際發佈。 |
| 5 | **做跨單位匿名試讀。** 同一主題與素材各準備現行流程稿與 AI 稿，合併學校、協會與公司的結果。 | 讀者按目的回答理解題，另評有趣程度與時事是否有幫助。承辦人逐篇核對可發布性。整體品質按試讀前約定的門檻判定。 |

## 試讀前需定案的量化設定

三類單位各測幾篇、每篇找幾位目標讀者、整體合併時如何加權，以及 AI 稿相對現行稿須達到的品質門檻。上述數字在收集試讀結果前定案。可先用同一張評分表區分發文目的是否達成、開場是否吸引人、時事或梗是否有幫助，以及承辦人的可發布性判定。
